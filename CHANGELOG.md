### Changed

- The optional `ioredis` peer dependency accepts `^5.0.0 || ^6.0.0` (in `mnemosy-ai` and `packages/legacy`); before, npm refused to install the package next to `ioredis` 6 (`ERESOLVE`). The repository now develops against ioredis 6 (`ioredis` ^6.0.0, devDependency). ioredis 6 requires Node.js 20 or newer; this package already requires 22.16.

### Fixed

- `fuzzy: true` could block the event loop on one long query token, even against an empty store. Candidate generation produced about 50 candidates per letter and checked each with a distance that scanned the full matrix, so cost grew with the cube of the token length: a 200-letter token took 4 s and a 4,000-letter one would have taken hours. A token longer than 48 letters is now matched exactly only, the distance computes only the diagonal band it needs, and at most 16 unmatched query terms are expanded per recall. A 4,000-letter token now takes about 5 ms, and a 4,096-character query made entirely of 48-letter tokens about 0.2 s. Ordinary words are matched as before.
- `indexMode: 'sqlite-vec'` failed in two cases. A recall whose candidate shortlist had to grow past 4,096 neighbours (a large `maxCandidates`, or widening on a store of more than 4,096 vectors) threw `k value in knn query too large`, because vec0 caps `k` at 4,096. The shortlist now stops at that limit and a recall that needs more is answered by the exact scan, which returns the same records and scores. Reopening a database with a different embedding model or dimension threw `no such table: main.local_vec_index`: the rebuild dropped the vec0 table before clearing the labels, whose erasure trigger still named it. The trigger is now dropped first and the table is recreated at the new width, inside the same transaction.
- With `indexMode: 'hnsw'`, a connection's dense channel missed records that another connection (or process) on the same database file embedded after the first one opened its graph. The graph lives in each process, and to the first connection those records were no longer pending, so it never added them. Before each search the graph now checks `PRAGMA data_version`, which moves only when another connection commits, and when it has moved adds every vector whose label is above its watermark. Erasures by another connection were already withheld, because each proposed label is re-authorized against the database.
- `importEmbeddings` checked only the byte length of a packed float32 vector, so a vector holding NaN, an infinity or only zeros was stored. Dense search then threw on that row, and re-embedding never replaced it because its source hash still matched. Such a vector is now rejected, with nothing written. A stored row that cannot be decoded (for example one written before this check) is skipped by exact, sqlite-vec and hnsw search instead of failing the query, and is marked so the next recall re-embeds it.
- Consolidation replay (Sol audit S01): the gate scored each task on a scratch copy built from `export()`, which holds only the agent's own records, while live recall also reads records other agents share with the workspace. A pass whose tasks were answered by a shared record scored 0 before and 0 after, so it was kept on evidence the replay never saw. A task whose gold, harmful or recorded result ids include a record live recall can read but the export lacks is now counted as unreplayable, so such a pass is `no_evidence` instead of `kept`. Not fixed: the replay still does not apply dense or hybrid ranking or the reranker, `kinds`, temporal bounds, metadata filters or precision controls, and a shared record that a task's recorded results did not include (for example one shared after the recall) is still absent from the scratch copy. The Honest limits section of `docs/CONSOLIDATION.md` now names each of these.
- Consolidation apply (Sol audit S02): `recordRetrievalOutcome` fills a recall entry's verifier slot in place without appending a ledger entry, so a verdict recorded from another connection between scoring and apply passed the gate's write check and the pass was kept on scores that no longer covered the replay set. The gate now rebuilds the replay set inside the apply transaction and returns `conflict` when its digest changed. `CONSOLIDATION_VERIFIER_SHA256` changes with these two rules.

### Security

- Two provider calls could still receive the text of a record forgotten after the call was started. `reflect()` compiled its context packet, then called the proposer from a queued microtask without re-reading the sources, so `reflect(...)` followed by a synchronous `forget()` sent the erased text. `indexGranularity()` read every pending derived document once, so a session or window document whose member was forgotten during an earlier batch (or right after the call started) was still embedded. Both now re-read at dispatch: `reflect` rejects with "Reflection evidence changed or became unavailable before dispatch" and sends nothing, and `indexGranularity` sends only documents whose stored hash still matches. The other paths that hand stored text to a provider (`indexEmbeddings`, `recallHybrid` and its reranker passes, runtime jobs and model refreshes, `AdaptiveContext.refresh`, `MemoryAgent.runTurn`) already rechecked at dispatch; erased records are deleted with their history, derived documents, ledger results and index entries, so `replay`, `export` and as-of recall cannot return them.
- `AdaptiveContext.build` ran a custom `tokenCounter` inside the database transaction that reads the context evidence. A `forget` made from inside the counter was therefore rolled back when the build then failed, which it does when a selected source disappears, and the erased text stayed stored. The counter now runs outside that transaction, so a deletion it makes commits on its own; the builder still revalidates every selected source afterwards and rejects a packet whose evidence changed. `MemoryBridge` already counted outside its transaction.
- `MemoryAgent.runTurn` checked context freshness at dispatch with a new read set that dropped `requireWatched` and recorded the state at that moment. A change between `beforeTurn` and dispatch, such as a removed watch, could therefore pass, and the host responder ran on a source that `requireWatched: true` should have withheld. This affected a host `contextBuilder` and a `contextProvider` whose `validate` does not recheck watches; the built-in builder revalidated its own packet. `runTurn` now revalidates the read set that `beforeTurn` created, with the same `requireWatched`, and fails with `context-failed` when it no longer holds.
- `startMemoryHttp` charged every request to its server-wide budget before checking the origin or the token. With `allowRemote`, about 1,000 unauthenticated requests a minute made authorized clients receive 429 until the minute ended; a principal over its own `requestsPerMinute` could do the same to other principals. The server-wide budget is now charged only after authentication and the principal's own budget. Requests without a valid token (the inspector shell, failed authentication, rejected origins) have a separate budget of 60 a minute per remote address and 1,000 a minute in total. The default loopback binding was affected only by local clients.
- Model setup (`npm run setup:embedder`, `npm run setup:reranker`, `fetchBundledModel`, `fetchBundledReranker`) staged each download at the fixed name `<file>.partial` and wrote it with a call that follows symlinks, then changed the target's mode by path. Another local user who could write to the model cache directory could plant a symlink there and have the download overwrite a file of the user running setup. Setup now stages under an unpredictable name created exclusively (`O_CREAT|O_EXCL`, plus `O_NOFOLLOW` where available), sets the mode on the open file, and renames into place, which replaces a symlink at the target rather than writing through it. A private cache directory, the default, was not exposed.

### Development

- Builds with TypeScript 7 (`typescript` ^7.0.2, devDependency). Two tests transpiled `src` files into a subprocess fixture through the TypeScript compiler API, which the TypeScript 7 package no longer exports; they now use Node's built-in `stripTypeScriptTypes` (`node:module`), so the fixtures add no dependency. The emitted JavaScript is byte-identical to the TypeScript 6 build; 16 declaration files differ only in quote style and member order, and the published declarations typecheck under both TypeScript 6 and 7.

## [3.0.0-rc.2] - 2026-10-28

The second 3.0.0 release candidate, and the first 3.0 release on npm. It is published on the
`next` channel (`npm install mnemosy-ai@next`, or pin `mnemosy-ai@3.0.0-rc.2`); npm `latest` stays
2.0.0, so unpinned installs are unaffected. It builds on rc.1 below, which was not published and is
folded into this release. Every benchmark number
reproduces offline, with no API key, no paid model and no LLM judge, using the command given next
to it (the latency figures come from a scratch harness that is not committed, and their protocol is
stated in full). The protocols and limits are in [docs/BENCHMARKS-TRUST.md](docs/BENCHMARKS-TRUST.md).
Measured on the merged tree `16cd9c0` (PrecisionMemBench reports re-run at that commit, no wrapper `kinds` predicate): 93 test files,
1,557 tests passed.

### Breaking

- **The legacy vector engine moved to `packages/legacy`.** `createMnemosyne`, the `./core`,
  `./cognitive`, `./graph`, `./broadcast`, `./pipeline`, `./cache` and `./tools` subpaths and the
  blind `dream()`/`consolidate()` consolidation are no longer in `mnemosy-ai`; they live unchanged in
  the separate package `mnemosy-ai-legacy`, which is **not on npm yet**. Build it from a checkout of
  this repository, or stay on `mnemosy-ai@2`, which keeps both engines. The import table and steps
  are in [docs/MIGRATION-v3.md](docs/MIGRATION-v3.md); the full list is under rc.1, "Removed
  (breaking)", below.
- **`mnemosy demo` runs the five-moment demo**, and the root `consolidate` export is a different
  function from the legacy one. Both are described under "Changed (behaviour)" below.

### Added

- **Precision controls in `recall()`.** The names gate, fuzzy matching, the metadata predicate and
  the score floors are opt-in, set either per call or as a `createLocalMemory` default; the
  lifecycle prefilter is always on. All of them are model-free on the lexical path.
  - **`requireNamedMatch: boolean | 'auto'` (names gate).** A record's `metadata.names` (a canonical
    name and its aliases) must occur in the query as a whole token phrase. With `'auto'` this
    applies only to records that declare names. The names stage is also a fused candidate
    channel, and `RETRIEVAL_STAGES` gains `'names'`.
  - **`fuzzy: boolean` (default `false`).** Guarded single-edit typo tolerance: OSA distance 1, the same first two
    letters, at least four letters, no digits, and half weight. It lives in `src/local/fuzzy.ts`.
  - **`metadata` predicate.** A string or string-array equality on metadata keys, evaluated in the
    SQL of every channel before ranking. It is capped at 32 keys and 64 values per key, and it is a
    scope selector, not an authentication boundary.
  - **Lifecycle prefilter (always on).** Every recall without an explicit `asOf`/`knownAt` drops
    superseded and expired records in SQL before ranking, on every channel (names, BM25, overlap,
    dense). This is a strict subset of what the as-of filter already withheld, so no recall
    returns a record it would have withheld before; see "Changed (behaviour)" below.
  - **Score floors.** `minScores: { keyword, semantic, reranker, final, finalRelative }`
    (`RecallScoreFloors`). Floors exclude results and never reorder them.
  - **Native abstention.** When nothing passes the gates, recall returns `[]`. The ledger's
    `retrieval.abstained` entry records `{ reason: 'no-candidates' | 'no-named-match' |
    'below-floor', floors, topScore }`, and `retrieval.config` records the controls in force.
  - **`ContextPacket.abstention` and `AdaptiveContextPacket.abstention`.** An empty packet says
    why it is empty. The reason is the recall's own, or `budget` or `withheld`.
- **`correct(id, { dependencies })`.** It adds declared dependencies to the successor (the old
  record's dependencies are always inherited), and it throws on duplicates and unknown ids. This
  is the only after-the-fact way to declare a dependency. It is ledgered, carries a reason, and its
  cascade reaches the successor through the new edge.
- **Ledger receipt events.** There are two new events, `consolidation` and `dependency`, and
  `LocalMemory.appendLedgerReceipt()` appends one inside the caller's transaction.
- **Outcome-gated, reversible consolidation** (`mnemosy-ai/consolidation`, also exported from the
  root). [docs/CONSOLIDATION.md](docs/CONSOLIDATION.md) describes it.
  - **Functions.** `proposeConsolidation`, `gateConsolidation`, `consolidate`,
    `rollbackConsolidation`, `verifyConsolidationChain` and `createConsolidationSigner`.
  - **What a pass is.** A signed diff (Ed25519) from a closed menu of proposals, checked against
    eleven invariants. It is replayed on the agent's own judged retrievals: the full set, a 20 %
    hold-out once there are at least 10 tasks, a no-memory control, and each proposal alone.
  - **Verdicts.** A pass is `kept` only when nothing regresses. The other verdicts are
    `rolled_back`, `no_evidence`, `invalid_run` and `conflict`, and every verdict writes a signed
    receipt that is hash-chained to the previous one.
  - **Rollback.** One call restores the identical `replayState().stateSha256`. It verifies the kept
    receipt first and reports `restored: true` only for an identical hash.
  - **Keys.** The gate trusts only its own signer's key by default; `trustedKeyIds: 'any'` is an
    explicit, unsafe opt-out. Any write between scoring and apply, and any reuse of an already kept
    diff, is a `conflict`. `--verify-chain` pins the store's key file when it exists.
  - **Backoff.** A faulted proposal is not proposed again until the replay set has doubled.
  - **CLI.** `mnemosy consolidate [scope] --propose [--out DIFF] | --apply [--file DIFF] |
    --rollback PASS_ID | --verify-chain`, plus `mnemosy consolidate --demo`. The signature format
    and chain are described in [docs/CONSOLIDATION-SIGNING.md](docs/CONSOLIDATION-SIGNING.md).
- **Undeclared-dependency inference** (`mnemosy-ai/dependencies`, also exported from the root).
  [docs/DEPENDENCIES.md](docs/DEPENDENCIES.md) describes it.
  - **`inferDependencies`.** Proposes (dependent, premise) pairs from successful co-use in traces,
    the retrieval ledger and outcome events (rule `co-use-success-v1`).
  - **`reviewDependency`.** A reviewer accepts or rejects each proposal. The decision is ledgered,
    and an acceptance goes through `correct(id, { dependencies })`.
  - **`createPremiseGuard`.** A read-only filter that holds a dependent whose co-used premise
    changed before anyone reviewed the pair.
  - **CLI.** `mnemosy dependencies [scope] --infer [--min-support N] [--json JSON]` and
    `--review DIGEST --accept|--reject --reviewer NAME [--reason TEXT]`.
- **Premise-linked skills (M6).** `MemoryRuntime.linkPremise(skillId, memoryId, receiptId)` links
  a skill to a premise named by an accepted `dependency` receipt. When that premise is corrected,
  `getSkill` reports the skill `retired`, and `trialSkill` refuses it. `RuntimeSkill.premises` and
  `premiseFingerprint` are added as optional fields.
- **`mnemosy demo` is the five-moment demo.** It runs offline, on synthetic corpora and the
  zero-model lexical path, and each moment prints a PROOF line measured in that run. The moments
  are: replay determinism; a correction that reaches dependents nobody linked; bisect; the
  poisoning suite run live; and a consolidation pass kept, another rolled back, and the kept one
  undone. [docs/DEMO.md](docs/DEMO.md) explains each one. The programmatic entry point is
  `runBreakthroughDemo()` in `src/evaluation/breakthrough-demo.ts`.
- **Poisoning suite consolidation mode.** `--consolidation` and `--ungated-control` are new flags
  on `dist/evaluation/poisoning/cli.js`. `dist/consolidation/rejected-passes.js` publishes every
  rolled-back pass with its receipt.
- **Dependency suite v1.** A synthetic corpus, generator and eval are in
  `benchmarks/dependencies/` and `src/evaluation/dependencies/`.

### Changed (behaviour)

- **The lifecycle prefilter is always on.** A recall without an explicit `asOf`/`knownAt` drops
  superseded and expired versions in SQL before ranking, so they no longer take candidate budget.
  No record that was withheld before is returned now, but a current record can enter the candidate
  budget where a superseded version used to crowd it out, so default results can differ when the
  candidate limits bind. LoCoMo and LongMemEval-S, which have no superseded records, are identical
  before and after (section 6 of `docs/BENCHMARKS-TRUST.md`).
- **`mnemosy demo` (and `npm run demo`) now runs the five-moment demo.** It streams text and exits
  1 if an implemented proof fails. The previous single-scenario JSON demo is `mnemosy demo
  --classic`, and `scripts/verify-package.mjs` now calls it that way. `demo --record FILE` saves
  the new report shape. To record the old shape, use `demo --classic --record FILE`.
- **The root export gains a `consolidate`.** It is the outcome-gated function above. It is not the
  legacy blind `consolidate()` that rc.1 removed: the name is the same, but the signature and
  semantics are different.
- **New package exports:** `./consolidation` and `./dependencies`. The root also re-exports
  `consolidate`, `createConsolidationSigner`, `gateConsolidation`, `proposeConsolidation`,
  `rollbackConsolidation`, `verifyConsolidationChain`, `inferDependencies`, `reviewDependency` and
  `createPremiseGuard`, plus the types `ConsolidationDiff` and `ConsolidationReceipt`.
- **New ledger `retrieval.config` keys.** `requireNamedMatch`, `fuzzy`, `minScores`, `kinds` and
  `metadataFilter` are written only when they are set. A recall that passes `kinds` therefore gets
  a different configuration hash, while calls without the new options keep their old hash.
- **`recallHybrid` rejects the precision options with a `TypeError`.** It does not apply them.

### Fixed

- **`mnemosy demo` moment 1 could intermittently hang for about 120 s and fail with a replay
  child-process timeout (`ETIMEDOUT`).** The replay input (about 73 KB) was passed to the child over
  stdin, which can stall on macOS; it is now passed as a file in the demo's temporary directory.

### Known limits

- **PrecisionMemBench.** The names gate abstains, by design, on queries that refer to a named
  record without naming it.
- **Latency.**
  - **The non-default `overlap` scorer is much slower.** With 400 superseded rows in the store,
    `recall({ lexicalScoring: 'overlap' })` is **+458 % p50** slower than the same build with the
    lifecycle prefilter disabled (26.6 ms against 4.8 ms; per-round range +414 to +694 %) and
    +517 % against 2.0.0 (4.6 ms), on the loaded-host protocol above. The prefilter is always on
    and has no switch. BM25, the default scorer, and hybrid recall are not affected, but MCP
    `memory_recall` and the CLI expose `lexicalScoring: 'overlap'`. The cause has not been
    investigated.
  - **Idle-machine latency is unmeasured.** Every latency figure above comes from a loaded host,
    and the per-round ranges are wide. The real embedder and reranker, stores larger than 2,400
    rows, and a premise guard with task evidence were not measured. An earlier loaded-machine
    before/after sample on 100 LongMemEval questions showed about +10–25 % p50.
- **Consolidation.**
  - Replay is lexical.
  - A store with the default `queries: 'digest'` ledger setting records no query text, so every
    pass on it is `no_evidence`.
  - `supersede` and `delete` proposals are never applied live.
  - The signing key lives in `<db>.consolidation.key` (mode 0600), and key-rotation receipts are
    not written yet.
  - In the suite the synthetic verifier never exercises a regression rollback.
  - Paraphrase laundering is not caught. `declared-content` is a token-subset test, so an
    untrusted instruction restated, without citing it, only in words from trusted records is kept
    as a live `procedure`.
  - No improvement from experience has been measured; the gate only keeps passes that do not
    regress recorded outcomes.
- **Dependencies.**
  - Stale = 0 holds only when the executor uses the premise guard. The kernel alone runs 7 stale
    procedures on the gate seed.
  - Stale = 0 also rests on the generator's observability floor (every true edge appears in at
    least one judged successful task); without it (`--no-floor`) stale is 1 on the gate seed and 2
    on seed 11. Precision is tested by the hub and incidental decoys only (295 of 405 decoys
    cannot count as support by construction).
  - The eval reviewer accepts everything, so precision on real controller traces is unmeasured.
  - Some thresholds and one corpus parameter were chosen after seeing results; all of these
    choices are disclosed.
  - Only the lexical path was measured.
- **Benchmarks not scored.** MemSecBench is not scored (it needs the authors' cases and paid judge
  calls), and ConsolidationBench is still blocked.

## [3.0.0-rc.1] — not published; folded into 3.0.0-rc.2

The first 3.0.0 release candidate. It was never tagged or published; everything in this section
ships in 3.0.0-rc.2 above. Numbers below reproduce from a fresh clone of
the branch with the commands in [docs/BENCHMARKS-TRUST.md](docs/BENCHMARKS-TRUST.md).

### Removed (breaking)

- **The legacy Qdrant/graph/broadcast/cognitive engine no longer ships in `mnemosy-ai`.** The
  `createMnemosyne` factory and default export, the `./core`, `./cognitive`, `./graph`,
  `./broadcast`, `./pipeline`, `./cache` and `./tools` subpaths, and with them the blind
  `dream()`/`consolidate()` consolidation, `runConsolidation`, `maintainMemory`,
  `runDreamConsolidation` and the Qdrant/FalkorDB/Redis clients, moved unchanged to
  `packages/legacy` as the private package `mnemosy-ai-legacy`. The root export is the kernel
  only. Read [docs/MIGRATION-v3.md](docs/MIGRATION-v3.md) for the import table and how to keep
  running the legacy engine. `src/connectors` stays (it never used Qdrant).

### Added

- **`LocalMemory.promote(id, { to, corroboration, reason })`** — raises a record's trust only
  when at least two active corroborators share no provenance ancestor with the candidate or
  with each other (rule `ancestry-disjoint-v1`). Every decision, granted or quarantined, is a
  `promotion` ledger event with a readable verdict; `ledger({ event: 'promotion' })` reads

## [2.0.0-rc.10] — Tier 1 retrieval, 2026-10-21

Tier 1 retrieval reconciled onto the published RC9 packaging and released on the `next` channel;

### Added

- **Opt-in dense index (`indexMode`).** `'exact' | 'auto' | 'sqlite-vec' | 'hnsw'`, defaulting to
  `$MNEMOSYNE_INDEX_MODE` else `'auto'`. `auto` uses `sqlite-vec` when the extension loads and
  otherwise falls back to the exact scan — still exact, just scored in C. `hnsw` is approximate and
  sublinear, is the only retrieval component that can miss a true neighbour, and is **never selected
  on your behalf**; asking for `sqlite-vec` or `hnsw` and not getting it throws rather than silently
  degrading. No mode changes what a record scores or whether it may be returned: every candidate an
  index proposes is re-authorized and rescored against the stored vector, so an index is a shortlist
  and never an authority. `c8f994c`, `0f244e5`, `7730916`, `ab60b9a`, `ef8458f`, `745c299`,
  `2dcdf7a`. **Its Tier 1 exit target, p95 recall latency under 50 ms at 1,000,000 records, is not
  met.** Hybrid `recall()` on a synthetic 1M-record `hnsw` fixture store (each query pays a real ONNX
  embedding pass, the search runs on the fixture's vectors; reranker off, ledger on) measured p95
  139.4, 146.9 and 223.3 ms in three fresh processes of 300 queries each, host load average 2–3.
  Commands and outputs are in `reports/t1-targets/`.
- **`sqliteVecPath`** — an explicit path to a `sqlite-vec` loadable extension, with deliberately no
  environment-variable equivalent, so a machine-wide variable can no longer decide what every
  `LocalMemory` on the host `dlopen`s. `a5b9db7`.
- **`cacheSize`** — passes through to `PRAGMA cache_size` (negative = KiB, positive = pages);
  default `-65536`, i.e. 64 MiB. `7034027`, with peak-RSS-at-1M-records measurements in `209184e`.
- **`hnswlib-node` pinned to exactly `3.0.0`** and `sqlite-vec` to `^0.1.9`, both as
  `optionalDependencies` so neither is required to install. `ca98458`.
- **Opt-in temporal routing** on `recall` and context compilation: a retrieval query's absolute and
  relative dates are parsed and can set an `asOf`, behind an explicit switch and a minimum parser
  confidence. A query-parsed clock can never reach past the present. `691c957`, `37374f0`,
  `9b08819`, `450360d`; the benchmark reports the temporal-reasoning subset separately in `b834028`. The same switch now
  also applies a when-intent prior (`a82d500`): when a query asks *when* something happened but
  carries no date the router can use, candidates whose own text carries a parseable date are promoted
  within a fixed depth. On the full LoCoMo set (1,531 annotated questions) the date window alone gains
  **+2.45 pts** recall@10 on the temporal category (79.92 → 82.37), **short of its +3.0 gate**; with
  the prior the gain is **+3.28** (79.92 → 83.20) and overall recall@10 rises 73.57 → 75.34, which
  meets the gate by 0.28 pts — less than one question, since each of the 320 temporal questions is
  worth 0.31. Against the date window alone the prior wins 10 temporal questions and loses 7, which is
  not a significant difference; on conversations 0–4 alone the prior gains only +2.24. Its pattern
  was designed by reading that same category, so the pass is in-sample and fragile; no out-of-sample
  check has been run. The LoCoMo benchmark now checks the gate's overall-floor half too (`9eda585`).
- **Cross-encoder reranking** of the fused candidate set, with a bundled int8 ONNX embedder that
  runs synchronously and offline. `72dcb20`, `ebb48ed`, `6503021`.
- **Contextual reranking (T1.3)** — a candidate is scored with its in-session neighbours rather
  than alone, bounded by `--rerank-context-top-n`. **This merged with its `g3` gate not met: the
  measured result is short of the gate by 0.82.** `a6bfb14`, `a6e98eb`, `2b948e4`, `b286fb4`.
- **Full-candidate provenance and outcome ledger** — the ledger records the complete retrieval
  candidate set rather than only what was returned. `1b146d7`, `a40e470`.
- **A matched competitor benchmark.** Competitor systems are scored as conditions inside our own
  `runCorpusBenchmark` loop — one process, one chunk set, one K, one packing budget, one evidence
  scorer — rather than having their published numbers quoted. Results, including every condition
  where Mem0 OSS beats us, are in [COMPARISON.md](COMPARISON.md). `cf031cf`, `868c8a8`, `79afea3`,

## [1.0.0] — 2026-02-23

### Added

- **Vector memory store/recall/forget** — Store, retrieve, and delete memories using dense vector embeddings via Qdrant for semantic search
- **BM25 hybrid search** — Combine sparse BM25 keyword matching with dense vector search for combined lexical and semantic retrieval
- **Spreading activation** — Graph-based spreading activation traversal that surfaces related memories contextually, even when semantic similarity is low
- **Temporal sequences** — Automatically discover and replay ordered event sequences; predict likely next events from a current trigger
- **Pattern mining** — Mine co-occurrence clusters, entity correlations, recurring errors, and anomalies from the memory corpus
- **Dream consolidation** — Background consolidation job that deduplicates, merges near-duplicate memories, strengthens frequently accessed facts, and prunes stale entries
- **Cross-bot synthesis** — Fleet-wide knowledge synthesis discovers consensus, contradictions, blind spots, and complementary knowledge across all agent instances
- **Conversation digests** — Automatically compress and summarize long conversation histories into concise, searchable digests
- **Observational memory** — Passive background observation mode that captures environmental signals and inferences without explicit store calls
- **Theory of Mind for Agents (TOMA)** — Query what a specific bot knows about a topic from its own perspective; supports multi-agent knowledge attribution
- **Memory-R1 feedback** — Reinforcement-style feedback loop (positive/negative signals) that promotes or demotes memories based on retrieval usefulness
- **Cognitive intent detection** — Automatically classify the intent behind incoming text (storing facts, querying, reflecting, planning) to route memory operations intelligently
- **Proactive queries** — Agents can subscribe to memory topics and receive push notifications when relevant new memories arrive
- **Knowledge graph via FalkorDB** — Persist entity relationships and semantic links in a property graph; enables multi-hop reasoning over stored knowledge
- **Cross-agent broadcast via Redis** — Publish memory events to a Redis pub/sub channel so all agents in a fleet receive real-time memory updates
- **Configurable backends** — Swap vector store (Qdrant), graph store (FalkorDB), document store (MongoDB), and cache (Redis) independently via environment variables
- **Auto-collection creation** — Collections are created automatically on first use with sensible defaults; no manual setup required
- **Ollama/OpenAI embedding support** — Generate embeddings locally via Ollama or via the OpenAI-compatible API; configure with a single env variable
- **Smart compaction** — Intelligently compact memory collections by merging redundant entries while preserving semantic coverage
- **Memory decay** — Time-aware decay weighting that reduces the retrieval score of old, unaccessed memories to surface fresher context
- **Memory feedback** — Per-memory signal API allowing callers to mark recalled memories as useful or wrong for continuous quality improvement
- **Fleet synthesis** — Aggregate and reconcile knowledge across a distributed fleet of agents into a unified, deduplicated knowledge base
- **Memory lessons** — Auto-extract actionable lessons, anti-patterns, gotchas, and corrections from conversation history
- **Memory preferences** — Track and surface inferred user or agent preferences (tools, languages, styles, workflows) with confidence scores
- **Memory sequences** — Discover temporal sequences (after A, B typically follows within N hours) and expose them for planning and prediction
- **Memory patterns** — Surface topic clusters, co-occurrence patterns, and correlation matrices mined from the stored memory corpus
- **Memory timeline** — Retrieve memories filtered and sorted by time range for chronological context reconstruction
- **Memory blocks** — Named shared memory blocks (fleet-wide working memory) readable and writable by all agents in the fleet
- **Memory consolidation** — On-demand deep consolidation: finds contradictions, merges near-duplicates, promotes popular memories, and demotes stale ones
- **Memory dream** — Asynchronous background dream consolidation pass with a status/report endpoint to check progress
- **Anomaly detection** — Identify statistically unusual memory entries or patterns that deviate significantly from established knowledge
- **Correlation analysis** — Compute and store pairwise correlation between memory topics and entities to reveal hidden relationships
