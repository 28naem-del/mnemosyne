# Peak RSS at 1,000,000 records — T1.2b (u6)

**Measured by:** `/usr/bin/time -l` wrapping the whole benchmark process, reading its
`maximum resident set size` line (bytes on macOS). Not `process.memoryUsage()` sampling — the
`-l` figure is the kernel's own high-water mark for the process, so it cannot miss a spike
between samples, and it includes the HNSW graph's off-heap allocation, which a V8-only
`heapUsed` reading would not see at all.

**Workload:** a warm 1M dense+lexical recall, i.e. the `measure` phase of
`scripts/benchmark-ann-scale.mjs` against the 1M fixture — one warm-up `recall()`, then 200 timed
hybrid `recall()` calls (dense + BM25) followed by 200 timed lexical-only `recall()` calls on a
second connection. The graph is the real 1.6 GB HNSW sidecar, loaded, not stubbed.

```
node scripts/benchmark-ann-scale.mjs measure \
  --mode hnsw --store .benchmark-ann/store1m.sqlite --queries 200 --max-candidates 1000
```

## Result

| run | maximum resident set size | peak memory footprint | wall | host load (1 min) |
|-----|--------------------------:|----------------------:|-----:|------------------:|
| 1 (cold page cache) | 2,254,684,160 B — **2.10 GiB** | 2,186,417,064 B — 2.04 GiB | 138.17 s | 12.71 |
| 2 (warm)            | 2,179,842,048 B — **2.03 GiB** | — | 116.69 s | 14.48 |
| 3 (warm)            | 2,255,781,888 B — **2.10 GiB** | — | 92.28 s | 15.39 |

**Peak RSS at 1M records: 2.10 GiB** (2,255,781,888 B, the highest of three runs).

## Reading it

- The number is **dominated by the HNSW graph, not by the engine**. The sidecar
  `store1m.sqlite-hnsw` is 1,684,514,548 B (1.57 GiB) on disk and `hnswlib-node` holds the graph
  resident, which accounts for ~75 % of the 2.10 GiB high-water mark. The remaining ~0.5 GiB covers
  the V8 heap, the bundled embedder/reranker ONNX sessions, and SQLite's page cache.
- **SQLite's page cache is a small and now-explicit part of it.** u6 ships `cacheSize` defaulting to
  `-65536` = a 64 MiB budget per connection. The `measure` phase holds two connections in sequence
  (hybrid, then lexical-only), so the PRAGMA accounts for at most ~128 MiB of the total, ~6 %.
  Raising `cacheSize` trades RSS for fewer page reads at a known, bounded rate — that is the point
  of making it an option rather than leaving SQLite's tiny built-in default in place.
- **The 4.2 GB main database is never fully resident**, and should not be: it is read through
  SQLite's pager, so the OS page cache (outside this process's RSS) absorbs the working set. This is
  why run 1, on a cold page cache, is the slowest of the three despite having the *lowest* footprint
  of the two 2.10 GiB runs — the cost showed up as wall time, not as RSS.
- **Caveat, stated rather than smoothed over:** every run above was taken on a host carrying two
  other concurrent builds at load average 12.7-15.4. Contention inflates wall time; it does not
  meaningfully move a high-water RSS mark, so the memory figure is the more trustworthy of the two
  columns here. Wall times in this file should not be quoted as latency results — the latency
  numbers live in RESULT.md with their own per-run load annotations.
