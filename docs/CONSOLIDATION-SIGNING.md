# Consolidation signing and the verdict chain (design note)

Status: design for the 3.0 consolidation gate (user guide: `docs/CONSOLIDATION.md`). Scope: what a consolidation diff is signed with, what the signature claims, and how gate receipts link into a verifiable chain.

## Objects

- **Diff.** Canonical JSON (code-unit key order, no whitespace) of `{ schema, stateBefore, candidateSet, proposals }`. `stateBefore` is `replayState(memory, { knownAt }).stateSha256` at the gate cut. `candidateSet` is the sorted list of `{ id, fingerprint }` the proposer was allowed to read, each `fingerprint` from `getRecordFingerprint(id)`. `proposals` are the closed-menu operations (`merge | supersede | split | delete | abstract`).
- **candidateDiffSha256.** SHA-256 over `mnemosyne-consolidation-diff-v1\n` + the canonical diff. This digest is what is signed.
- **Receipt.** One `consolidation` ledger event per gate decision or rollback, written with `appendLedgerReceipt` inside the same transaction as the apply or the rollback. `digest` = SHA-256 over the canonical receipt without `digest`; `prevDigest` = the previous receipt's `digest` in the same workspace and agent scope (`null` for the first).

## Where the key lives

Recommendation in the brief: a per-store Ed25519 keypair kept inside the database (`local_settings` or a new `local_keys` table). **This cannot be done from outside the kernel today.** `local_settings` exists and holds the cursor secret, but it is reachable only through `LocalMemory`'s private `#db`. The consolidation module is not allowed to modify `src/local/index.ts`, and opening a second `DatabaseSync` on the same file from a module would bypass the kernel's transaction and permission handling.

v1 therefore uses, in order:

1. **Key file next to the database (default for file stores).** `createConsolidationSigner({ keyFile })` creates `<db>.consolidation.key` on first use with `open(path, 'wx', 0o600)` (exclusive create, so two processes cannot race to different keys), refuses symlinks and non-regular files, re-asserts `0600` on every open, and stores a PKCS#8 PEM Ed25519 private key generated by `node:crypto`. `*.key` is already excluded from the npm `files` list.
2. **Caller-supplied key** (`{ privateKey }` as a `KeyObject` or PKCS#8 PEM) for hosts that keep keys in an OS keychain or HSM bridge.
3. **Ephemeral key** for `:memory:` stores and tests. Receipts signed with it verify, but the key dies with the process; a verifier that pins key ids will reject them later.
4. **Fixed seed** (`{ seed }`, 32 bytes) only for the synthetic poisoning suite and reproducible fixtures, so reports are byte-reproducible. A seed key is public by construction and must never sign a real store.

Every diff and receipt carries `signature: { algorithm: 'ed25519', keyId, publicKey, value }`: `publicKey` is the raw 32-byte key (base64url), `keyId` is SHA-256 of those bytes (hex), `value` is the base64url signature. A future kernel accessor (CONSULT in the unit report: `LocalMemory.settings(namespace)` returning a get/set view over `local_settings` rows prefixed with the namespace) would let the private key move into the database file, which already gets `0600` from the kernel; the receipt format would not change.

Alternatives considered:

- **HMAC-SHA-256 with a store secret** (it could reuse a `local_settings`-style secret). Cheaper and dependency-free, but symmetric: anyone who can verify can forge, so a receipt cannot be checked by a second party without handing them the forging key. Rejected as the default.
- **No key, hash chaining only.** The `prevDigest` chain alone detects edits, reordering and truncation in the middle of the chain, but anyone with write access to the file can recompute the whole chain. Kept as the always-on layer under the signature, not as the only one.

## What a signature means

A valid signature means exactly: **the holder of key `keyId` ran this store's consolidation module over a store whose state hash was `stateBefore`, allowed it to read exactly the records in `candidateSet` with those fingerprints, and it produced these proposals.** Together with the receipt it also fixes which replay set (`replaySetSha256`) and which gate code (`verifierSha256`) judged the diff.

It does **not** mean that the proposals are true, that a merged text is a faithful summary, that the sources are authentic, that the host's scope or evidence labels are honest, or that the outcome improvement generalizes beyond the recorded replay set. Trust labels are still host assertions; the signature only binds the gate's inputs to its output. The replay gate, not the signature, decides keep or roll back.

## Threat model

| Threat | Defense | Verdict |
|---|---|---|
| Forged or edited diff file (tampered export, edited JSON between `--propose` and `--apply`) | Recompute `candidateDiffSha256`; verify the Ed25519 signature; optional pinned `keyId` list | `invalid_run` |
| Replay of an old, validly signed diff on a newer state | Recompute `stateBefore` at apply time; it must equal the diff's | `conflict` |
| Diff claiming a different `stateBefore` than the records it lists | Every candidate fingerprint is recomputed; any missing or changed record fails | `conflict` |
| Proposal reading outside its candidate set or declaring sources it did not use | P9 invariants: dependencies inside the candidate set; derived tokens covered by declared sources | `rolled_back` |
| Laundering an untrusted record into a policy-tier record | Invariant: no `procedure`/`decision` at trust ≥ `observed` may draw content from an untrusted record | `rolled_back` |
| Edited, deleted or reordered receipt | `verifyConsolidationChain` recomputes each `digest`, checks `prevDigest` links and each signature | chain error |
| Attacker with write access rewrites the whole chain and the key file | Not defended locally; pin `keyId` out of band (for example in a release or a second machine) | out of scope |

Snapshots: `export()`/`import()` carry records and outcomes, not ledger receipts, so an imported store starts a fresh chain; the importing store must re-run the gate rather than trusting a foreign receipt. The public key travels inside every diff and receipt; distributing or pinning it is the host's decision.

## Key rotation

Rotation is append-only. A new key signs a `rotation` receipt (verdict `kept`, no proposals) whose payload names the previous `keyId` and carries a signature by the old key over the new `keyId`; the chain continues through it. Old receipts stay verifiable with the public key embedded in them. Losing the old private key means the next receipt cannot carry a link signature. v1 verifies mixed-key chains and lists every key change in `keyChanges` instead of silently accepting it; with `pinnedKeyIds`, a receipt signed by any other key fails verification. Writing the rotation receipt itself is a known gap in v1.

## Verdict digest chain

```
receipt_n.prevDigest = receipt_{n-1}.digest
receipt_n.digest     = sha256("mnemosyne-consolidation-receipt-v1\n" + canonical(receipt_n without digest))
```

`verifyConsolidationChain(memory)` pages through `ledger({ events: ['consolidation'] })` in sequence order and checks, for each receipt: the schema, the recomputed digest, the link to the previous digest, the signature over `candidateDiffSha256` (when the receipt has one), and that every `rollback` receipt names a kept pass that was not already rolled back. It returns `{ ok, receipts, head, keyChanges, errors }`. Erasure of a record does not remove consolidation receipts (they are appended without `memoryId`) and receipts hold record ids and fingerprints but never record text.
