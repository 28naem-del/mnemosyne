# Consolidation signing and the verdict chain (design note)

Status: design for the 3.0 consolidation gate, implemented in `src/consolidation/` (user guide: [CONSOLIDATION.md](CONSOLIDATION.md)). Scope: what a consolidation diff is signed with, what the signature claims, and how gate receipts link into a verifiable chain.

## Objects

- **Diff.** Canonical JSON (code-unit key order, no whitespace) of `{ schema, workspaceId, agentId, cut, stateBefore, candidateSet, proposals, proposer }`. `stateBefore` is `replayState(memory, { knownAt: cut }).stateSha256`. `candidateSet` is the sorted list of `{ id, fingerprint }` the proposer was allowed to read, each `fingerprint` from `getRecordFingerprint(id)`. `proposals` are the closed-menu operations (`merge | supersede | split | delete | abstract`). The scope fields stop a diff signed for one agent from being applied to another.
- **candidateDiffSha256.** SHA-256 over `mnemosyne-consolidation-diff-v1\n` + the canonical diff without `digest` and `signature`. The diff signature is over `mnemosyne-consolidation-diff-signature-v1\n` + this digest.
- **Receipt.** One `consolidation` ledger event per gate decision or rollback, written with `appendLedgerReceipt` inside the same transaction as the apply or the rollback. `digest` = SHA-256 over `mnemosyne-consolidation-receipt-v1\n` + the canonical receipt without `digest` and `receiptSignature`; `prevDigest` = the previous receipt's `digest` in the same workspace and agent scope (`null` for the first). `receiptSignature` is the store key's signature over `mnemosyne-consolidation-receipt-signature-v1\n` + `digest`, so a receipt is attributable even when it carries no diff (`invalid_run`, `rollback`). The receipt also carries `scores` (`tasks`, `before`, `after`, `delta`, `holdout`, `noMemory`, `unreplayable`, `perProposal`), the invariant results, each proposal's `proposalSha256` with a `fault` flag the proposer's backoff reads, and the created ids with fingerprints.

## Where the key lives

Recommendation in the brief: a per-store Ed25519 keypair kept inside the database (`local_settings` or a new `local_keys` table). **This cannot be done from outside the kernel today.** `local_settings` exists and holds the cursor secret, but it is reachable only through `LocalMemory`'s private `#db`. The consolidation module is not allowed to modify `src/local/index.ts`, and opening a second `DatabaseSync` on the same file from a module would bypass the kernel's transaction and permission handling.

v1 therefore uses, in order:

1. **Key file next to the database (default for file stores).** `createConsolidationSigner({ keyFile })` creates `<db>.consolidation.key` on first use by writing and syncing the key in a private `0600` temporary file and hard-linking it into place (never overwriting, so two processes cannot race to different keys and the path never names a partial key), refuses to replace an existing key file that does not parse, refuses symlinks and non-regular files, re-asserts `0600` on every open, and stores a PKCS#8 PEM Ed25519 private key generated by `node:crypto`. `*.key` is already excluded from the npm `files` list.
2. **Caller-supplied key** (`{ privateKey }` as a `KeyObject` or PKCS#8 PEM) for hosts that keep keys in an OS keychain or HSM bridge.
3. **Ephemeral key** for `:memory:` stores and tests. Receipts signed with it verify, but the key dies with the process; a verifier that pins key ids will reject them later.
4. **Fixed seed** (`{ seed }`, 32 bytes) only for the synthetic poisoning suite and reproducible fixtures, so reports are byte-reproducible. A seed key is public by construction and must never sign a real store.

Every diff and receipt carries `signature: { algorithm: 'ed25519', keyId, publicKey, value }`: `publicKey` is the raw 32-byte key (base64url), `keyId` is SHA-256 of those bytes (hex), `value` is the base64url signature. A future kernel accessor (CONSULT in the unit report: `LocalMemory.settings(namespace)` returning a get/set view over `local_settings` rows prefixed with the namespace) would let the private key move into the database file, which already gets `0600` from the kernel; the receipt format would not change.

Alternatives considered:

- **HMAC-SHA-256 with a store secret** (it could reuse a `local_settings`-style secret). Cheaper and dependency-free, but symmetric: anyone who can verify can forge, so a receipt cannot be checked by a second party without handing them the forging key. Rejected as the default.
- **No key, hash chaining only.** The `prevDigest` chain alone detects edits, reordering and truncation in the middle of the chain, but anyone with write access to the file can recompute the whole chain. Kept as the always-on layer under the signature, not as the only one.

## What a signature means

A valid signature means exactly: **the holder of key `keyId` ran this store's consolidation module over a store whose state hash was `stateBefore`, allowed it to read exactly the records in `candidateSet` with those fingerprints, and it produced these proposals.** Together with the receipt it also fixes which replay set (`replaySetSha256`) and which gate code (`verifierSha256`) judged the diff.

It does **not** mean that the proposals are true, that a merged text is a faithful summary, that the sources are authentic, that the host's scope or evidence labels are honest, or that the outcome improvement generalizes beyond the recorded replay set. Trust labels are still host assertions; the signature only binds the gate's inputs to its output. The replay gate, not the signature, decides keep or roll back.

## Threat model

| Threat | Defense | Verdict |
|---|---|---|
| Forged or edited diff file (tampered export, edited JSON between `--propose` and `--apply`) | Recompute `candidateDiffSha256`; verify the Ed25519 signature | `invalid_run` |
| Diff validly self-signed by a foreign key | `trustedKeyIds` defaults to the gate signer's own `keyId`, and the CLI pins the store key | `invalid_run` by default. With the explicit, unsafe opt-out `trustedKeyIds: 'any'`, such a diff is judged like the store's own. |
| Replay of an old, validly signed diff on a newer state | Recompute `stateBefore` at apply time; it must equal the diff's | `conflict` |
| Replay of a diff that was already kept, after its rollback restored the identical state | A kept `candidateDiffSha256` is single-use | `conflict` |
| A write between scoring and apply (insert, correction, forget, outcome) | Record the scope's ledger high-water mark before the snapshot. At apply, require no later ledger entry and an unchanged current state | `conflict` |
| Diff claiming a different `stateBefore` than the records it lists | Every candidate fingerprint is recomputed; any missing or changed record fails | `conflict` |
| Proposal reading outside its candidate set or declaring sources it did not use | P9 invariants: dependencies inside the candidate set; derived tokens covered by declared sources | `rolled_back` |
| Laundering an untrusted record into a policy-tier record | Invariant: no `procedure`/`decision` at trust ≥ `observed` may cite an untrusted record or carry a token found only in untrusted records | `rolled_back` when the record is cited or such a token appears. An uncited paraphrase built only from trusted tokens is **kept** (not defended; see [Honest limits](CONSOLIDATION.md#honest-limits)). |
| Edited, reordered, or deleted receipt with a later receipt still present | `verifyConsolidationChain` recomputes each `digest`, checks `prevDigest` links and each signature; `rollbackConsolidation` verifies its kept receipt before acting | chain error; rollback refused |
| Tail truncation: the last receipt(s), or every receipt, deleted | Links cannot see it: the remaining prefix is a valid chain, even with the key pinned. Keep an earlier `head` where the database writer cannot reach it and pass it as `expectedHead` | Chain error ("expected head is not in the chain") with `expectedHead`, for truncation at or before that checkpoint. **Not detected** without it: `ok` then means the receipts present are intact, not that none are missing. |
| Database write access only (no key file): the whole chain re-signed with a fresh key | `mnemosy consolidate --verify-chain` pins the key in `<db>.consolidation.key`, and `--rollback` and the library default pin the signer's key | Chain error ("not pinned") and rollback refused. Not detected by `verifyConsolidationChain` without `pinnedKeyIds`, nor by the CLI on a store with no key file. |
| Database write access **and** the key file | Not defended locally: holding both is enough to rewrite the chain undetectably. Pin `keyId` out of band (for example in a release or on a second machine) | out of scope |

Snapshots: `export()`/`import()` carry records and outcomes, not ledger receipts, so an imported store starts a fresh chain; the importing store must re-run the gate rather than trusting a foreign receipt. The public key travels inside every diff and receipt; distributing or pinning it is the host's decision.

## Key rotation

Rotation is append-only. A new key signs a `rotation` receipt (verdict `kept`, no proposals) whose payload names the previous `keyId` and carries a signature by the old key over the new `keyId`; the chain continues through it. Old receipts stay verifiable with the public key embedded in them. Losing the old private key means the next receipt cannot carry a link signature. v1 verifies mixed-key chains and lists every key change in `keyChanges` instead of silently accepting it; with `pinnedKeyIds`, a receipt signed by any other key fails verification. Writing the rotation receipt itself is a known gap in v1.

## Verdict digest chain

```
receipt_n.prevDigest = receipt_{n-1}.digest
receipt_n.digest     = sha256("mnemosyne-consolidation-receipt-v1\n" + canonical(receipt_n without digest))
```

`verifyConsolidationChain(memory)` pages through `ledger({ events: ['consolidation'] })` in sequence order and checks, for each receipt: the schema, the recomputed digest, the receipt signature (against `pinnedKeyIds` when given), the link to the previous digest, the signature over `candidateDiffSha256` (when the receipt has one), and that every `rollback` receipt names a kept pass that was not already rolled back. With `expectedHead` (the `head` of an earlier verification, retained outside the database), it also requires a receipt with that digest to still be in the chain, so deleting receipts up to that checkpoint fails; receipts appended after it are accepted. It returns `{ ok, receipts, head, keyChanges, errors }`. Without `expectedHead`, deleting the last receipts or all of them leaves a chain that verifies. Without `pinnedKeyIds`, a chain consistently re-signed end to end with a different key verifies, so pin the key whenever it is known; `mnemosy consolidate --verify-chain` pins the store's key file when it exists. Erasure of a record does not remove consolidation receipts (they are appended without `memoryId`) and receipts hold record ids and fingerprints but never record text.
