# V0 — replay and memory bisect

Two read-only diagnostics for a local store. **Replay** reconstructs the belief state at a bitemporal cut
point and hashes it, so the same store and the same cut point produce the same digest in any process.
**Bisect** takes a retrieval failure and delta-debugs the visible record set down to a small set of records
whose removal restores the expected result.

Both are opt-in. Neither changes the schema, neither writes to the store, and a CLI run that does not name
them does not load their code.

## Replay

A cut point is a pair: `--known-at` is transaction time (what the store had been told by then) and
`--as-of` is valid time (what was true of the world at that moment). `--as-of` defaults to `--known-at`.

```sh
mnemosy replay --db memory.sqlite --workspace demo --agent a \
  --known-at 2030-01-01T00:00:00.000Z --hash
```

```
9156232ddf4a5025a7ec669e63b004b0b742e4f3d84e62d1ae5048cd2e999315
```

The digest covers the records visible at that cut point — id, kind, text, source, trust, validity and
transaction stamps, dependencies and invalidation — canonically serialized with keys sorted by UTF-16 code
unit. It deliberately excludes derived state: embedding blobs, search indexes, the ledger, `audit`,
`idempotency` and `outcomes`. Two processes on two machines that hold the same records agree on the digest
even if their indexes were built differently. The cut point itself is not part of the hash, so two
different cut points that produce the same belief state produce the same digest.

`--records` prints the state instead of the digest. `--diff` compares two cut points and names each change
with its source:

```sh
mnemosy replay --db memory.sqlite --workspace demo --agent a \
  --known-at 2026-09-15T07:27:00.000Z --diff 2030-01-01T00:00:00.000Z \
  --json '{"knownAt":"2030-01-01T00:00:00.000Z"}'
```

```json
{
  "algorithm": "mnemosyne-replay-state-v1",
  "from": { "cut": { "knownAt": "2026-09-15T07:27:00.000Z", "asOf": "2026-09-15T07:27:00.000Z" },
            "stateSha256": "5323f867…", "records": 0 },
  "to":   { "cut": { "knownAt": "2030-01-01T00:00:00.000Z", "asOf": "2030-01-01T00:00:00.000Z" },
            "stateSha256": "0b5a439a…", "records": 2 },
  "added": [ { "id": "7eaab664…", "text": "The deploy key rotates every 30 days",
               "source": { "uri": "chat://standup/2026-02-11" }, "ledger": [ … ] } ],
  "removed": [], "changed": []
}
```

Every entry in `added`, `removed` and `changed` carries that record's ledger provenance — which source
introduced it, when, and the SHA-256 of its text. The ledger array is elided above for length.

## Bisect

A bisect task names a query, the record ids that count as the right answer (`gold`), and the rank cut-off
the answer is judged at (`k`). Optional fields: `asOf`, `knownAt`, `require` (`any`/`all`),
`lexicalScoring`, `depth`, `includeUntrusted`.

```sh
mnemosy bisect --db memory.sqlite --workspace demo --agent a \
  --json '{"id":"key-rotation","query":"deploy key rotates","k":1,"gold":["e233b376…"]}'
```

```json
{
  "taskId": "key-rotation",
  "blame": ["7eaab664-5995-4546-b2ac-1be989d2d72c"],
  "candidates": 2, "universe": 1, "tests": 0, "goldRank": 2,
  "minimalUnique": true, "alternatives": 0,
  "exactConfirmed": true, "exactMinimal": null,
  "outcome": "blamed", "reason": "displaced",
  "elapsedMs": 12.15
}
```

Read that as: the expected record sits at rank 2 when the task asks for rank 1, and removing the one
record in `blame` is what puts it back. `--file TASKS.json --task ID` reads the same shape from a file.

The search runs delta debugging (ddmin; Zeller & Hildebrandt, *Simplifying and Isolating Failure-Inducing
Input*, IEEE TSE 2002) over the retrieval candidates, against two oracles:

| | how it decides | cost | what it is blind to |
|---|---|---|---|
| **A — cached-rank ablation** | drops the ablated ids from one cached ranking | microseconds | corpus statistics that shift when records leave: BM25 IDF and average document length |
| **B — exact re-execution** | exports the store minus the ablated closure, imports it, re-runs recall | seconds | nothing in the retrieval path |

Oracle A drives the search; oracle B confirms the answer. `exactConfirmed` is B's verdict that the
proposed set really does fix the failure. `--exact` promotes B to the search itself: exact, and measured at
171.7 s on one N = 20 task against a 5.5 s median for the default path.

Oracle B re-executes the store's own retriever, read off `retrieval`: the zero-model lexical path, or the
default `hybrid` path. On hybrid it rebuilds with the source's embedding model, `rrfK`, `minSimilarity`,
reranker setting and dense index kind, and re-embeds nothing — a snapshot carries no vectors, so the stored
ones are copied across byte-for-byte (`exportEmbeddings` / `importEmbeddings`, keyed by memory id and text
hash) and only the query is embedded, by the same pinned model. After each re-execution the rebuilt
store's reported configuration must equal the source's, and `exactConfig` in the result is that
configuration. A difference throws instead of comparing two retrievers: a custom embedder or reranker has
to be passed in `storeOptions`, asking for a different path than the store uses (e.g. `retrieval:
'lexical'` on a hybrid store) is refused, and so is an `hnsw` index, whose approximate graph depends on
insertion order. The `mnemosy bisect` CLI still opens its auditor on the lexical path.

A blame set that B will not stand behind is reported as `outcome: "unconfirmed"` with the reason, not
quietly published. The other outcomes are `passing` (the task already succeeded), `unfixable` (no
ablation of the candidate set restores the answer) and `blamed`.

The candidate universe excludes the gold records **and everything they depend on**: ablating a record the
gold hangs off deletes the gold with it, so removing it could never make the task pass.

## What was measured

Built from `feat/v0-replay-bisect` at base `e94a261`. `npm run build` is a precondition of every command
below. The bisect harness needs a LoCoMo corpus at `benchmarks/data/locomo10.json`; that file is not in the
repository (see `npm run benchmark:fetch`). The result files these tables were read from (`k1.json`,
`k10.json`) are not committed either, so the numbers below are reproduced by re-running the commands,
not by reading a stored report. Times are from that one machine and vary with the machine.

### Replay determinism

```sh
npx vitest run tests/local-replay-determinism.test.ts
node scripts/replay-cut-hashes.mjs --db STORE --workspace W --agent A --cuts cuts.json | shasum -a 256
```

1000 random `(asOf, knownAt)` cut points over a seeded 100-record timeline with 125 validity boundaries:

| check | result |
|---|---|
| hash stream across 3 independent processes | byte-identical, 1000/1000 |
| same, under `TZ=Asia/Tokyo LC_ALL=tr_TR.UTF-8` | byte-identical |
| after `VACUUM`, `REINDEX`, `ANALYZE` and an embedding-cache rebuild (72 embeddings, file 495 616 → 565 248 bytes) | 1000/1000 hashes unmoved |
| as-of answers vs ground truth computed from the generating plan | 18 000 assertions over all 1000 cut points, 0 mismatches (10 475 present, 7 525 null) |

Distinct hashes in that run: 297. Cut points that replay the empty state: 128, so the effective sample is
about 872.

### Memory bisect

```sh
node scripts/benchmark-bisect.mjs --tasks 20 --counts 1,5,20 --k 1  --out k1.json
node scripts/benchmark-bisect.mjs --tasks 20 --counts 1,5,20 --k 10 --out k10.json
```

A 10 000-record store built from real LoCoMo text (5 882 turns, 2 541 observations, 272 session summaries,
668 event summaries, 637 sentence splits). For each fault count N, N competing false claims are planted per
targeted question — only questions that answer **correctly before** injection are targeted, so the planted
record is genuinely the cause. Blame precision is the share of blamed records that were planted; recall is
the share of planted records that were blamed. Time-to-locate is wall-clock per task.

**k = 1** — 19 of 20 questions displaced:

| N | precision | recall | median TTL | p95 TTL | exact-confirmed |
|---|---|---|---|---|---|
| 1 | 100.0% | 100% | 3.0 s | 5.0 s | 100% |
| 5 | 99.1% | 100% | 5.8 s | 8.3 s | 100% |
| 20 | 99.5% | 100% | 4.7 s | 6.6 s | 100% |

**k = 10** — the harder regime, reported because it is the honest one:

| N | displaced | precision | recall | median TTL | p95 TTL | unconfirmed |
|---|---|---|---|---|---|---|
| 1 | 0/20 | not measured | not measured | — | — | 0 |
| 5 | 6/20 | 90.6% | 53.3% | 3.9 s | 4.5 s | 0 |
| 20 | 20/20 | 93.0% | 67.9% | 5.5 s | 7.9 s | 1 |

At k = 10 and N = 1 a single planted record displaced nothing, so there was no failure to bisect and no
number to report. That row is a real miss, not a gap in the harness.

Against the proof gates — blame precision ≥ 90%, median time-to-locate < 60 s on a 10k-record store — both
regimes pass, k = 1 by a wide margin and k = 10 by 0.6 points at N = 5.

## Limits

- **The verifier is retrieval-based.** A task passes when the gold record ids appear within the top k. It
  does not read an answer, and no model judges anything. That is what makes the harness deterministic and
  free to run, and it is also the ceiling on what these numbers mean: they measure whether the right
  evidence is retrievable, not whether an answer built from it would be right. Verifying generated answers
  is a later unit.
- **At k = 1 the blame set is forced by the experiment's shape.** A question is only targeted if its gold
  is already at rank 1, so the only set that restores rank 1 is every record now above the gold. In all 57
  published k = 1 bisects `blame.length === goldRank - 1`. The 99–100% there measures how cleanly the
  planted records occupy the ranks above the gold. The regime where the answer is genuinely ambiguous is
  k = 10.
- **"Minimal" means 1-minimal with respect to the oracle used.** Re-executing one ablation per blamed
  record (`--confirm minimal`) shows that at N ≥ 5 about 80% of blame sets are minimal under exact
  re-execution; the rest fix the failure but are not the smallest set that does. Confirming minimality at
  N = 20 costs a 51.0 s median and a 61.8 s p95 — at the edge of the 60 s budget. The published numbers use
  the fast oracle for the search and the exact oracle for confirmation.
- **One recall returns at most 100 results**, because the kernel validates `limit` at 100. Deeper rankings
  are reached by *widening*: re-running the real recall with everything seen so far ablated, up to 3 times
  by default, for an effective depth of 400. Each widening costs a full re-execution, and the result is
  marked `ranking: "stacked"` — the later entries were ranked in a corpus the earlier block had already
  left, so their scores were not all computed against the same statistics.
- **The timeline corpus is small** — 100 records, 125 boundaries. Real bitemporal structure, not scale.
- **These are local lexical measurements.** No embedding model, no network and no paid call is involved in
  any command on this page.
